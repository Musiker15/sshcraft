# SSHCraft Teilplan R6: Steuerung Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Steuerung von außen: die Agent-Verbindung der laufenden App (Loopback, Token je Start, `agent-connection.json`), der Control-Channel für Entwickler (`--control`), das MCP-Crate und das Programm `sshcraft-cli`, die Anbindung an den ArtCraft Launcher, dazu die Abnahme-Liste aus Spec Abschnitt 10 vollständig.

**Architecture:**
- **Ein Draht, zwei Dienste.** Das neue Crate `sshcraft-link` (L1) hält das Protokoll: JSON-Zeilen, Grenzen, Anmeldung per Challenge (HMAC-SHA256, der Token geht nie über die Leitung), Token- und Verbindungsdatei, Client und Server. Die Engine bedient darauf die Agent-Verbindung (nur `engine.*`, alles als `Caller::Agent`), die App darauf den Control-Channel (`engine.*` als `Caller::Control`, dazu `ui.*`, `terminal.read`, `app.quit`).
- **MCP ist eine dünne Hülle.** `crates/mcp` (L6) spricht MCP über stdio und ruft über ein `Backend`-Trait `engine.execute`; das einzige echte Backend ist `Remote` (die laufende App über `agent-connection.json`, oder `--bridge` an einer `--control`-App). Eine Engine im Prozess gibt es nur in Tests.
- **Kein Betrieb ohne Fenster** (Spec 9.3): `sshcraft-cli` öffnet nie die Datenbank. Ist die App zu, gilt `--when-closed error|launch`.
- **Zustimmung** (Spec 9.2): ohne Flag `AI-MCP` entscheidet "Allow agent control" in den Einstellungen allein; mit dem Flag müssen dieser Schalter und `craft_ai_agents::allowed("sshcraft")` beide an sein. Die App prüft den Launcher alle 2 s.

**Tech Stack:** wie R5. Neu: `hmac`, `sha2` (schon im Baum über russh), `hex`, `getrandom` (alle MIT OR Apache-2.0), `clap` für `sshcraft-cli`, `craft-flags` aus craft-libs `cebc847`, `craft-ai-agents` aus craft-ai-integrations (Apache-2.0, auf eine Revision gepinnt, `allow-git` in `deny.toml`). Jede Fassung mit `cargo search` geprüft.

**Spec:** `docs/superpowers/specs/2026-11-14-sshcraft-craft-neuaufbau-design.md`, Abschnitte 6.2, 9.1 bis 9.4, 10, 13 (Zeile R6), 17. Vorlage für das Protokoll: `docs/control-protocol.md` und `docs/mcp.md` von photocraft (Challenge-Anmeldung, `agent-connection.json`, Grenzen). ## Global Constraints

- **Arbeitsbaum** `G:\Claude\worktrees\sshcraft-r6`, Zweig `r6-control`, von `origin/main` nach dem Merge von PR #12.
- **Sprache:** Code, Kommentare, Doku, Commits englisch, Aufgaben-Id je Commit (`R6.3: agent link`). Kein KI-Hinweis. Oberflächentexte englisch im Code, deutsch in `i18n/de.rs`. Plan deutsch.
- **Nur Loopback:** jeder Listener bindet `127.0.0.1`, nie eine andere Adresse, nie HTTP. Ein Client nimmt nur `127.0.0.1:<port>` und `[::1]:<port>` (kein Namensauflösen).
- **Token:** 256 Zufallsbits (`getrandom`), 64 Hex-Zeichen, nie im Log, nie in einer Antwort, nie auf der Kommandozeile der App. Die Tokendatei ist nur für den Besitzer: unter Unix Modus 0600 beim Anlegen; unter Windows liegt sie im Benutzerprofil, dessen ACL nur Benutzer, SYSTEM und Administratoren zulässt (kein `unsafe` für eigene ACLs).
- **Anmeldung nur per Challenge:** `auth.challenge {clientNonce}` → `{serverNonce, serverProof}`, dann `auth {proof}`; Beweise sind HMAC-SHA256 mit dem Token (64 Hex als ASCII) über `<label>\n<clientNonce>\n<serverNonce>`, Labels `sshcraft-link-v1 server` und `sshcraft-link-v1 client`. Der Client prüft `serverProof`, bevor er etwas sendet; ein Rückfall auf den Token im Klartext existiert nicht. Vor der Anmeldung wird nichts verarbeitet.
- **Grenzen:** Anfragezeile 1 MiB, Antwortzeile 8 MiB (zu groß → Fehler statt Abbruch), 16 Verbindungen je Listener, 10 s für die Anmeldung, 64 gleichzeitige Anfragen je Verbindung. Eine angemeldete Agent-Verbindung hat keine Leerlaufgrenze (ihre Sitzungen leben mit ihr).
- **Agents erreichen nur, was die Prüfung aus R2 zulässt:** jede Anfrage der Agent-Verbindung läuft als `Caller::Agent { name, via }` über `Session::execute`; `ui.*` und Screenshots gibt es dort nicht. Der Control-Channel ruft die Engine als `Caller::Control` (gleiche Prüfung).
- **Kein Shell-Text:** `--when-closed launch` startet die App über `std::process::Command` mit Argumentliste.
- **Datenformate bleiben:** Schema 11, Keyring-Dienst, Datenordner. `agent-connection.json` hat `version: 1`.
- **Nie abstürzen:** Eingaben aus dem Netz und von stdin sind feindlich (Zeilen begrenzen, JSON-Tiefe durch serde begrenzt, Indizes mit `get`).
- **Gegenproben** für jeden Test einer Regel, eines Rechts oder eines Datenwegs (Anmeldung, Caller der Anfragen, Zustimmung, Abnahme-Liste).
- **Jede Aufgabe endet mit grünem `cargo xtask ci` in PowerShell.**

## Review Focus

1. **Ein fremdes Programm lauscht auf dem Port aus einer alten `agent-connection.json`** (App abgestürzt): Erwartet: der Client erfährt nichts über den Token, weil der Lauscher `serverProof` nicht liefern kann; die Meldung sagt "SSHCraft is not running" (Test `a_listener_without_the_token_learns_nothing`, Task 1).
2. **Ein Agent schickt über die Agent-Verbindung `ui.click`, `app.quit` oder eine Anfrage ohne Anmeldung**: Erwartet: abgelehnt, nichts passiert, die Verbindung schließt nach der fehlenden Anmeldung (Tests `agents_get_no_ui_methods`, `nothing_runs_before_auth`, Task 3).
3. **Das MCP-Programm endet mitten in einer offenen Agent-Rückfrage und mit offenen Sitzungen**: Erwartet: die Rückfrage verschwindet als abgebrochen im Protokoll, die Sitzungen enden (Test `a_gone_mcp_process_ends_its_sessions_and_questions`, Task 5).
4. **"Allow agent control" ist aus, der Launcher aber an (oder umgekehrt mit Flag)**: Erwartet: kein Listener, keine `agent-connection.json`; Abschalten im Betrieb trennt bestehende Agent-Verbindungen und löscht die Datei (Test `the_link_follows_the_consent`, Task 4).
5. **Ein Agent flutet das Protokoll durch viele schnelle Anfragen über die Verbindung**: Erwartet: das Protokoll bleibt bei 1000 Einträgen, die App bleibt bedienbar (Test `an_agent_cannot_flood_the_log_through_the_link`, Task 8).
