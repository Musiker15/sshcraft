# SSHCraft Teilplan 6: Client-Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Die Desktop-App gleicht Hosts, Gruppen und (wählbar) Schlüssel über einen oder mehrere eigene Sync-Server ab: Konto anlegen, weiteres Gerät mit dem Kontoschlüssel einrichten (Einfügen, QR-Anzeige), live und offline abgleichen, Geräte auflisten und sperren mit Schlüsseltausch.

**Architecture:** Ein neues Crate `crates/sshcraft-sync` enthält alles, was mit einem Server spricht: einen HTTP-Client (`ServerClient`), die Kontoabläufe (anlegen, beitreten), die Abgleich-Logik (Abholen, Senden, Konflikte) und eine Laufzeit je Server mit WebSocket und Wiederverbindung. Der lokale Zustand (Server, Bereiche, Versionsstände, Ausgang) liegt im SQLite-Store von `sshcraft-core` (Schema 3), Geräteschlüssel nur verschlüsselt im Tresor. Die App bindet das über neue Tauri-Befehle und eine Sync-Seite in den Einstellungen an. Getestet wird gegen den echten `sshcraft-server` im selben Prozess.

**Tech Stack:** Rust 1.99, sshcraft-proto, sshcraft-core, sshcraft-server (nur Tests), reqwest 0.13.5 (`default-features = false`, Features `json`, `rustls`), tokio-tungstenite 0.30.0 (Feature `rustls-tls-webpki-roots`), hkdf 0.13.0, qrcode 0.14.1 (Feature `svg`, ohne Standard-Features), tokio, serde; Oberfläche React 19 mit Vitest.

**Spec:** `docs/superpowers/specs/2026-11-11-sshcraft-design.md`, Abschnitte 4 (Ort), 5 (Schlüsselquellen), 6 (Konto anlegen, Anmelden, Geräte und Geräte-Sperre), 7 (Sync: Einstellungen pro Server, mehrere Server, Ende-zu-Ende, Angreifermodell, live und offline); dazu `docs/protocol.md`, `docs/server-api.md` und der Fahrplan.

## Global Constraints

- Alle Regeln der Teilpläne 1 bis 5 gelten weiter (Arbeitsbaum unter `G:\Claude\worktrees`, Code Englisch, Commits Deutsch ohne KI-Zuschreibung und ohne Gedankenstriche, UTF-8, Gegenproben für Regeln, Rechte und Datenwege, ohne Remote nach grünen Tests lokal in `main` mergen).
- **Immer die neueste Paketversion, vor jedem Eintragen geprüft:** `cargo info <crate>` bzw. `npm view <paket> version`. Die Versionen oben sind der Stand vom 12.11.2026.
- **Der Server sieht nur Chiffrat.** Alles, was ein Gerät synchronisiert, geht nur als `SealedRecord` hinaus; Namen, Adressen und Schlüssel stehen nur im verschlüsselten Inhalt.
- **Der Client prüft alles, was vom Server kommt:** Geräteprotokoll mit `DeviceLog::verify_extends` gegen den zuletzt bekannten Kopf, Manifeste und Datensätze über `VersionTracker::accept_manifest`/`accept_record`, Umschläge mit `open_area_key` gegen das geprüfte Manifest. Was nicht besteht, wird verworfen und als Warnung gemeldet, nie übernommen.
- **Geheimnisse:** Geräteschlüssel nur über den Tresor versiegelt gespeichert; der Kontoschlüssel wird nie gespeichert, nur beim Anlegen angezeigt und beim Beitreten aus der Eingabe benutzt und danach genullt (`Zeroizing`). Nie loggen: Kontoschlüssel, Geräteschlüssel, Bereichsschlüssel, Sitzungs-Token, API-Key, Inhalte von Datensätzen.
- Oberflächentexte nur über die Übersetzung (en, de), Fehler aus Rust nur als `ErrorCode`.
- **[Claudes Entscheidung] Wiederherstellungsgerät:** Bereichsschlüssel gehen nur an Geräte (HPKE). Damit "ist kein Gerät mehr übrig, richtet man mit dem Kontoschlüssel ein neues ein" (Spec 6) die Daten erreicht, leitet `sshcraft-proto` aus dem Kontoschlüssel ein festes Gerät ab (Plattform `recovery`), das beim Anlegen ins Protokoll kommt und jeden Umschlag bekommt. Wer den Kontoschlüssel hat, hat damit auch dieses Gerät; mehr Macht als der Kontoschlüssel ohnehin gibt es nicht.

## Review Focus

1. **Derselbe Host auf zwei Geräten offline geändert**, danach gehen beide online: Am Ende zeigen beide Geräte dieselbe, die später geänderte Fassung; nichts doppelt, kein Löschen geht verloren. Test in Task 7.
2. **Einrichten scheitert** (Server nicht erreichbar, falscher API-Key, Origin passt nicht, E-Mail vergeben, Kontoschlüssel mit Tippfehler oder von einem anderen Server): klare Fehlermeldung, kein halb angelegter Server in der Liste, nichts im Tresor zurückgelassen. Tests in Task 5.
3. **Gerät wird gesperrt, während es offline ist:** Beim nächsten Verbinden erkennt es `device_inactive`, hört auf zu synchronisieren, zeigt "Dieses Gerät wurde gesperrt" und behält seine lokalen Daten. Test in Task 8.
4. **Host zeigt auf einen Schlüssel, der nicht mitsynchronisiert wird** (Schlüssel-Sync aus oder Agent-Schlüssel): Auf dem anderen Gerät erscheint der Host mit dem Hinweis "Schlüssel fehlt", Verbinden meldet das sauber. Tests in Task 4 und 11.
5. **Server liefert einen älteren oder fremd signierten Stand** (Rückfall, Gabelung, Datensatz von einem gesperrten Gerät): wird verworfen, der lokale Stand bleibt, die Laufzeit meldet eine Warnung statt abzustürzen. Test in Task 6.
